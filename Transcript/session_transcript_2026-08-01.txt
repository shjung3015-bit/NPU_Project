check my Systolic_Array.sv, Top_module.sv, SRAM.sv, MAC_Unit.sv. Since my
SRAM's output is 32bit and whole Systolic Array is 4*4 which every MAC Unit
handles 8bits each, in Loading Weight Phase, I thought that I need to

ASSISTANT:
Full-system review (Controller + Systolic_Array + Top_Module + SRAM +
MAC_Unit + SKEW_Unit).

Confirmed the user's architecture understanding is correct: SRAM dout is
32-bit = 4 lanes of int8; wgt_in[k] loads one row of the 4x4 weight matrix
per read (needs 4 reads total, one per row, shifted down via w_out); act_in
feeds one scalar per row via the diagonal skew (single 32-bit read is
correct for a weight-stationary GEMV: one 4-element activation vector ×
stationary 4x4 weights → one 4-element output vector).

Root cause identified: SRAM.sv's dout is registered (1-cycle read latency:
"ask this cycle, get it next cycle"), but Controller's enb_wgt/load_en/
enb_act/start are all produced through a registered always_ff keyed off
current_state, adding ANOTHER cycle of lag on top — nothing accounts for
SRAM's extra cycle.

Weight loading bug (traced cycle-by-cycle): addr_wgt changes every cycle
(combinational) but enb_wgt turns on one cycle late, so the address for
offset=3 is requested while enb_wgt is still 0 and is silently dropped;
instead you get 2,1,0 plus a stale duplicate of 0. Net: array only shifts
in 3 distinct weight rows instead of 4, deepest row ends up as 0.

Activation bug (traced cycle-by-cycle): `start` (single-shot pulse driving
SKEW_Unit's valid_in) fires exactly the cycle enb_act turns on — one cycle
BEFORE dout_act actually reflects the read (SRAM's own 1-cycle latency).
SKEW_Unit latches stale/leftover data and marks it valid; the real data
arrives one cycle later with `start` already back to 0.

Fix direction proposed: add one more cycle of buffer between "enable
asserted" and "consumer treats data as valid," either via a delayed
load_en/start, or (better, refined in turn 7) by making enb_wgt/enb_act
combinational so they align with addr_wgt/addr_act in the same cycle,
letting the existing 1-cycle lag on load_en/start naturally match SRAM's
latency.

Separate smaller bug: act_offset only reset to 0 inside the ACT branch
itself, not reloaded in IDLE like wgt_offset — on a second `run` without an
intervening reset, the first ACT cycle would use the stale leftover
act_offset (=3) instead of 0.

[5] USER:
Can I just change some flipflop posedge -> negedge to solve this problem?

ASSISTANT:
No. Two reasons:
1. Doesn't address the root cause — the missing piece is a pipeline stage
   (SRAM's own registered read), not "wrong edge." Shifting some flops to
   negedge only moves things by half a cycle, and in the activation case
   you actually need `start` to happen LATER, not earlier — an edge swap
   pushes the wrong direction (or at best half of what's needed).
2. Mixed-edge synchronous design is fragile in real hardware (relies on
   ~50% clock duty cycle for timing margins) and is hard to reason about /
   often flagged by STA tools.

Recommended clean fix instead: make enb_wgt/enb_act/addr outputs
combinational (same cycle as the state), and let load_en/start's existing
one-cycle registered lag be the thing that matches SRAM's one-cycle read
latency — i.e., make the "enable" instant and use the natural lag on the
"consume" signal instead of stacking two separate lags.

Bug #1 (weight row loss) table, base_addr_wgt=100:
  Cycle1: addr=103, enb=0 (not ready yet) -> request lost forever
  Cycle2: addr=102, enb=1 -> captures mem[102]

  => row 103 never read; only 3 of 4 rows loaded.

Bug #2 (stale activation) table:
  Cycle A (ACT): enb_act=0, start=0
  Cycle B (WAIT#1): enb_act=1 (just turned on), start=1 (pulses here) but
    dout_act is STILL the old leftover value (SRAM hasn't finished the read)
  Cycle C (WAIT#2): dout_act finally correct, but start already dropped to 0
  => SKEW_Unit latches garbage, marks it valid; correct data arrives with
     nobody listening.

Explained why negedge doesn't fix this: both bugs are "something fires
before the data it needs is ready" — needs a full extra cycle of delay,
which a half-cycle edge shift can't reliably provide, and for bug #2 you
need MORE delay, not less.

Real fix in plain terms: delay the "go/consume" signal by one more tick
using an explicit delayed copy of enb (e.g. enb_wgt_d <= enb_wgt;) to gate
load_en/start; separately, fix bug #1 by making addr_wgt and enb_wgt turn on
together (same cycle) instead of enb lagging addr.

[11] USER:
I was considering to put data continuously . (Not now but after checking
thr whole system.) So, which way do you think better, extending wait
stage or adding dedicated done/valid output?

ASSISTANT:
Recommended the dedicated valid signal, given the stated future goal of
continuous/streaming operation.

Reasoning: extending WAIT to cover the full 8-cycle latency would force the
Controller to sit idle the whole drain time before considering a new run —
defeating the systolic array's whole point (pipelined throughput). It's
also a hardcoded magic number that breaks if the array is resized later.

Pointed out the needed signal already exists, just unexposed: each
MAC_Unit's out_valid faithfully tracks when its psum_out is fresh, and for
row 3 it currently dead-ends into an unused sink (in_valid_array[3][4] in
SYSTOLIC_ARRAY.sv). Recommended exposing this as a new
`output logic [3:0] data_valid` (one bit per output column) on
Systolic_Array, routed up through Top_Module.

Noted WAIT would still need a small fixed margin (not full drain) just to
protect against overwriting weights while old activations are still
in-flight — a separate, much smaller concern from full-result completion.
