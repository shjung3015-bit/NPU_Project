- Streaming 4 different row-vectors back-to-back didn't give 4 distinct rows either - each row's register just kept getting overwritten as later frames passed through it, so every row ended up holding the last frame sent, not its own intended vector.

I asked the user how to proceed (fix weight loading first / testbench current behavior only / explain a different intended protocol). The user chose: "Fix weight loading first."

The fix, in three parts:

1. SKEW_Unit.sv - dropped `wgt_in`/`wgt_skew_in` entirely; it only needs to skew activations and valid now.

2. MAC_Unit.sv - weight capture/shift is now gated only by `load_en` (unconditional each cycle it's high), independent of `in_valid`:
```
if(load_en) begin
    w_reg <= w_in;
    w_out <= w_in;
end
else if (in_valid) begin
    a_out <= a_in;
    psum_out<=psum_in + a_in * w_reg;
end
out_valid<=in_valid;
```

3. Top_Module.sv - feed `wgt_in` straight into row 0 (bypassing the skew unit), and drop the now-unused `wgt_skew_in` wiring: `assign w_array[0][k] = wgt_in[k];`

For compute, a single activation pulse makes `data_out[j]` valid `j+4` clock edges after the edge that sampled it (column 3 is the slowest, arriving at edge+7).

Wrote a new file `tb_Top_module.sv`:
- Loads a random 4x4 weight matrix `W` by presenting its rows in reverse order (row 3, 2, 1, 0) over 4 cycles with `load_en=1` - lands `W[i]` in PE row `i`.
- Streams one random activation vector `A` with a 1-cycle `start` pulse, waits out the worst-case 7-edge latency (column 3), then reads `data_out`.
- Checks against a software golden model `expected[j] = sum_i A[i]*W[i][j]`, repeats for 5 random trials, reports PASS/FAIL per column.

Here's the full breakdown of the weight-loading fix.

The original bug:
`wgt_in` was routed through `SKEW_Unit` - the same diagonal-skew network used for `act_in`. That network is a set of per-row shift-register chains (row i delayed by i extra cycles), with no way to stop a value at a target row. Once a weight value entered at row 0, it just kept sliding down through row 1, 2, 3, one cycle at a time, forever (as long as `in_valid`/`load_en` stayed asserted).

Combined with the old MAC_Unit logic (capture gated by `in_valid`), every row's `w_reg` got overwritten every time a value passed through it. So if you streamed 4 different row-vectors meant for 4 different PE rows, each row would just keep capturing whatever was passing by, and by the time everything settled, every row ended up holding the last vector sent - not its own intended row. There was no way to load a real 4x4 matrix with distinct values per row; you could only broadcast one shared vector to all rows.

Why skewing was never needed for weights in the first place:
Diagonal skewing exists so that `act_in`, `psum`, and their `valid` flags stay aligned in time as they ripple across the 2D mesh during compute - row i needs to be i cycles ahead of row 0 so its data reaches column j at the same moment row 0's data does. Weight loading has no such alignment requirement: you're not computing anything yet, you just want each row's register to hold a fixed value before compute starts. That's a plain shift-register problem, not a skew problem.

The fix:
1. SKEW_Unit.sv - stripped out `wgt_in`/`wgt_skew_in` and the `wgt_bubble` registers entirely. It now only skews `act_in` and `valid_in`.
2. MAC_Unit.sv - decoupled weight capture from `in_valid`: weight shifting now happens on every cycle `load_en` is high, unconditionally - a straightforward 4-deep shift register down each column, with no dependency on the activation-skew machinery at all.
3. Top_Module.sv - `wgt_in` is wired straight to `w_array[0][k]` (bypassing `SKEW_Unit` completely); `SKEW` now only produces `act_skew_in` and `valid_out`.

Why "reverse row order" loads it correctly:
With a plain 4-deep shift register (no skew), after pushing 4 values v0, v1, v2, v3 (one per cycle, in that order), the register ends up holding row0=v3, row1=v2, row2=v1, row3=v0 - the last value pushed ends up at the top (row 0), and the first value pushed ends up furthest down (row 3). So to get row_i = W[i], you must push v_c = W[3-c] - i.e. present row 3 first, row 0 last. That's exactly what `load_weights()` in the testbench does.
